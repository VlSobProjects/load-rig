# Roadmap

The destination is stated in [`brief.md`](brief.md): produce the injector side of every capture
the `load-test-triage` scenario needs, answer the SUT specification's questions, and hold the
constraints the exchange documents bind this project to.

Each item is a unit of work with its own session. An item's number is its identity, not its
place; the order of this document is the order of the work. A row is rewritten, not appended to.

| # | Item | State |
| --- | --- | --- |
| LR-1 | **The transport skeleton.** Form login with the CSRF token scraped per session — the fragments carry none, and a browser holds the token of the page it loaded — the fragment answer shape held for a whole run, the identity of a task and of a provisioned account read out of the answers that produced them, one walk per role, and the password change a fresh account is held at | done |
| LR-9 | **The account pool.** The accounts a run signs in with, decoupled from the fresh database's three: how many the profile needs and how many of them are managers — the discussion scenario needs managers who are not the creator of the task they comment on — held as explicit configuration and provisioned against the stack through the administrator screens LR-1 walked. Half of the LR-4 answer, and the ground the registries are exercised on. The walk retires when the SUT's seeding item takes the whole initial state; until then its idempotence is the guarantee that a seeded stand meets a no-op | done |
| LR-2 | **The session and task registries.** SUT sessions decoupled from virtual users and picked by state; the task registry mirroring the SUT's transition table so a step finds a task it may act on; unit-tested against that table without a running stack | done |
| LR-3 | **The day profile.** The step mix, the hot-set skew, the per-step think times and the population equilibrium of the specification, with the equilibrium invariant checked by the rig rather than trusted | done |
| LR-4 | **The answers owed to the SUT project.** Accounts and managers count, mix survival, the convergence mechanism, the intensities and skew as explicit configuration — delivered through the exchange desk | done |
| LR-5 | **The run harness and the capture artifacts.** A documented command per run; the JTL configuration with explicit timestamp semantics; the load-profile description authored per variant; the artifact layout a capture consumes | done |
| LR-10 | **The warm start and the scaled balance.** The population the profile needs, computed per bucket from the scenarios' own weights instead of assumed, and established before the window by a warm start that reads what the stand already holds from the list page ordered by due date — the only inventory the application offers — and creates the difference. Pure creation on an empty stand and pure reading on a seeded one, so the SUT's seeding item costs it no rewrite; stand administration and not load, so the result log holds the window alone. With it, the run's work circulates among the accounts the run occupies: a pool sized to the campaign's ceiling no longer sends most of a smaller run's creations to people nobody signs in as. The profile's untrue seeded volume goes with it: the stand's volume is measured at the warm start and published beside the census, and the equilibrium is judged on the working set the steps draw from rather than on a figure nobody measured (DR-6) | done |
| LR-6 | **The service levels as the rig's own criterion.** The figures the SUT specification chose, held as the configuration of a campaign and not of a profile: one file, fixed before the campaign and carried into every capture's description, so that a baseline and the faulted run it is read against are judged by the same numbers. Every sample the result log carries is timed into the band of the act that produced it, and a run states the percentile it realized per band against the level it was held to, by a percentile method it names rather than assumes. A breach is published as a finding and never fails a run, because the injector-side variants are meant to breach; and the verdict is the injector's half and says so, the quiet application log and the flat throttled-period counter being read on the stand. With it the first measured baseline of the day profile, which is the fifth answer owed to the SUT project | done |
| LR-13 | **The density of the profile: a population that turns over, and a stand that starts the same.** Measured on the calibration probe rather than supposed: with the seats fixed nobody signs in after the ramp, so the band that measures signing in measures a cold start; the people a step draws its lists, its tasks and its report subjects from are as few as its seats; and the one band that moved across the ladder moved with the volume the stand held rather than with the intensity. So a session ends at a stated share and another begins, the account that signs in is chosen from the rig's own registry by what it holds, the players are wider than a step's seats with the depth a campaign parameter, DR-6's circulation rule is amended to the accounts a run plays over its window with the census stocking all of them, the initial state — how many play and how many tasks the stand holds — is stated by the campaign and levelled to in both directions by the warm start, and deletion runs at a stated share with its pick unbiased (DR-8) | pending |
| LR-14 | **The generator in a container, driven from a command line.** The core map allots the generator one pinned physical core pair and forbids it the system's cores and the collectors'; nothing enforces that today, because the rig runs as a JVM the host's scheduler places where it likes, started from a development environment sitting on the same host. The SUT project's letter of 2026-09-03 names a closed host and a rig driven from its own containers as the two conditions before a run on that stand carries a verdict. So an image for the rig and a compose file of its own - its own project, as the stack's Grafana is, so a reset of the stack never takes it - joined to the stack's network, holding the `cpuset` the map allots, with the results root mounted out so captures outlive the container. The alternative is a hand-set affinity mask on the host plus a checklist of what to close before a run: it costs almost nothing and is rejected because it fails silently - a run started the usual way carries no mask and says nothing about it, and a checklist leaves no trace in the capture of whether it was performed, while a `cpuset` declared in a file is in force on every run and visible to the collectors, so the capture itself can show where the generator ran. With it the addresses stop being `localhost` and become the stack's own names | pending |
| LR-15 | **The readings the rig takes for itself.** DR-9's closed list, read from the stack's own collectors: both halves of the calibration rule - the throttled-period counters of the application and the database, and the application's log over the window - then processor use per container against its quota, memory against its limit, the connection pool's active, idle and waiting, and the rate the stack actually saw. Every figure states the limit it is read against, because a figure without its limit has already produced a published wrong conclusion in this project. Taken over the window the figures are computed from and not over the run, so that the cold-start burst the SUT project measured across 2026-08-31 - the counter above zero in exactly two minutes of the day, both of them the first minute of a run - never discards a step for the wrong reason. A reading that cannot be taken is recorded as not taken, with its reason, and the run stands (DR-9) | pending |
| LR-16 | **The panels, rendered per run.** The window's panels fetched through the SUT stack's renderer into the protocol's own directory, by the dashboard `uid` and the panel numbers that project states as a contract with this one - configuration here and never literals, and never reused for a different panel. What makes the protocol a document a load-testing project hands over rather than a table of numbers, and what the SUT project receives instead of an invitation to measure the same window again (DR-9) | pending |
| LR-17 | **A campaign of several steps in one command.** The steps of a search stated in the campaign file and driven in one command, each laying its own capture and its own protocol under the campaign's directory, with the stand levelled back to the campaign's stated initial state between steps (DR-8) and a settling interval before each measured window opens, so no step's figures carry the warm-up burst the calibration rule reads as throttling. What lets a closed host stay closed: a campaign that needs nobody at the keyboard between its steps is the difference between a valid capture and a supervised one | pending |
| LR-11 | **The stepped maximum-finding run.** The same profile shape with the intensity raised proportionally in steps - the populations scaled and the census with them - each step a capture of its own, the first step that misses the criterion ending the search and the step before it standing as the maximum for this configuration. The criterion is not the comfort figures the baseline met by one to two orders of magnitude: the search is a campaign of its own, judged by levels derived as one multiple of what the same stand answered when it was quiet, with the multiple fixed by a calibration run that is spent rather than published (DR-7). So the search terminates while the response curve is still graded, and a step counts only if it drove the intensity it intended and judged its bands on samples enough to decide one. What turns the specification's assumed ceiling of twenty virtual users into a measurement, or refutes it: a ceiling probe that is really an overload run produces captures of the wrong kind of test, and one ended by the injector or by a saturated pool reproduces a planted fault instead of finding a maximum. It runs last of the calibration work - after LR-13, and after the container, the readings and the campaign runner of LR-14 to LR-17, because a step whose validity nobody on this side can read is not a step: the calibration probe found no knee below eighty virtual users, the generator holding its target within a few percent throughout, so the search has nothing to measure until the profile is dense enough to load the stand — and the quiet reference the criterion is derived from cannot be the campaign's coldest run, which is what the baseline turned out to be | pending |
| LR-12 | **The morning and evening profile variants.** The specification states their shares as high, moderate and low on purpose, and pinning them is this project's choice rather than a number it received. Morning leans on the wide read whose cost the index decides, evening on the transitions that hold a connection for the length of a request, and the day profile stays the comparison run both are read against - which is what lets an analysis say which fault it is looking at, not merely that something is wrong | pending |
| LR-7 | **The injector-side defect variants.** The flooding thread group, the starved injector and the injector dying mid-run, each applied deliberately per variant | pending |
| LR-8 | **The Gatling transport poc.** The LR-1 scenarios on Gatling's Java DSL in a `poc/` branch: per-sample export viability and cross-user coordination under the async model, measured against the same stand | pending |
